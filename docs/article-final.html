1. “Who Does Reddit Think Wins?” (SERP API)

The idea

BattleBots fans argue constantly on Reddit about which robot would beat which. I wanted to turn those arguments into a structured verdict. Pick Tombstone vs Minotaur, and instead of reading 40 Reddit threads yourself, let the machine do it.

The data problem

I needed Google search results for Reddit discussions about specific robots. Not the Reddit API (which limits what you can search). Google’s index of Reddit, which is much richer.

Why SERP API

Bright Data’s SERP API lets you send a Google search URL and get back structured JSON instead of raw HTML. The magic parameter is brd_json=1. Append that to any Google search URL, and Bright Data parses the results for you: titles, URLs, descriptions, ranking positions. No HTML parsing. No Puppeteer. Just a POST request and clean data back.

I could’ve used Google’s Custom Search API (100 free queries/day, then paid) or scraped Google directly with rotating proxies. I went with SERP API because brd_json=1 meant zero parsing code on my end and I could focus on the fun part: the sentiment analysis.

How the pipeline works

For each matchup, I fire 6 Google searches in parallel (3 per bot: “bot vs opponent”, “bot + weapon type”, “bot + opinion”). That gives me 40-80 Reddit results. I run keyword scoring to tag each result as positive, negative, or neutral. Then Claude Haiku 4.5 reads the scored evidence and writes a verdict with cited Reddit quotes.

The keyword scoring is rough on purpose. It’s not trying to be accurate. It’s giving the LLM structured context so it can write a better narrative than it would from raw text alone.

The result looks like a sports analyst’s take, with actual Reddit sources backing every claim. Try it yourself.

2. “Every Robot, Structured” (Web Unlocker)

The idea

A searchable database of 30 BattleBots with win/loss records, weapon types, team info, season appearances. Think of it as a Pokedex for combat robots.

The data problem

The best source for this data is the BattleBots Fandom wiki. Detailed pages for every robot, updated by fans after every season. One problem: Fandom uses aggressive bot protection. A regular fetch() call returns 403 every time. They’re behind Cloudflare’s anti-bot layer, which detects headless browsers, blocks datacenter IPs, and serves CAPTCHAs.

Why Web Unlocker

Bright Data’s Web Unlocker is essentially a proxy that handles all the anti-bot stuff for you: browser fingerprinting, CAPTCHA solving, IP rotation, cookie management. You send it a URL, it returns the page content as if a real human visited it in a real browser.

The killer feature for me was data_format: "markdown". Instead of getting back raw HTML that I’d need to parse with cheerio or jsdom, I get clean markdown. For a wiki page, that’s almost perfect: headings, tables, lists, all preserved and ready to work with.

I scraped 8 pages total (5 bot profiles + 3 canonical sources). The output feeds the encyclopedia frontend directly.

Could I have used Puppeteer with stealth plugins? Possibly. But Fandom’s detection has gotten aggressive enough that I didn’t want to spend days fighting it. Web Unlocker got me the data in an afternoon. See the encyclopedia.

3. “Most Watched Fights, Ranked” (YouTube Scraper)

The idea

Which BattleBots fights have the most views on YouTube? Which ones get the most comments? I wanted a leaderboard that you can sort by views, likes, comments, or controversy (comment-to-like ratio).

The data problem

YouTube has an API, but it’s quota-limited (10,000 units/day, a single search costs 100 units) and requires OAuth setup. I didn’t need real-time data. I needed a one-time collection of fight videos with their engagement metrics.

Why YouTube Scraper

Bright Data’s YouTube Scraper (part of their Web Scraper API) works differently from the other products. It’s asynchronous. You tell it “find YouTube videos matching this keyword,” it runs the collection in the background, and you poll until it’s done. Takes 30-90 seconds, then you download structured results: title, URL, thumbnail, views, likes, comments, duration, upload date.

I could’ve used yt-dlp (free, no quotas) to extract video metadata. The tradeoff: yt-dlp needs to be installed locally and you’d have to handle the YouTube search part separately. Bright Data’s scraper handles search + metadata extraction as one step.

The real win was getting real thumbnails. Every YouTube video has a thumbnail at https://img.youtube.com/vi/{VIDEO_ID}/hqdefault.jpg. I used these across both the YouTube Ranker and the Fight Gallery, so two apps got real images from one data source. Check the ranker.

4. “What’s Happening in BattleBots?” (Crawl API + SERP)

The idea

An aggregated news feed pulling from battlebots.com, Reddit, the wiki, Hollywood Reporter, and anywhere else that publishes BattleBots content.

The data problem

News lives on a lot of different websites. I needed to both find articles (search) and read their content (crawl). Two different operations.

Why Crawl API + SERP

For discovery, I used the same SERP API from the H2H project. Searching Google for “battlebots 2025 news” returns real articles from real publishers.

For content extraction, I used Bright Data’s Crawl API. Same POST-to-/request pattern as the other products, just with a crawl_api zone. It fetches the page, handles any bot protection, and returns the content. With data_format: "markdown", I get clean readable text instead of HTML soup.

The News Hub now shows 28 articles from 14 different sources: battlebots.com, Hollywood Reporter, Reddit, the wiki, TripAdvisor (people review the live show), and more. Browse the news.

5. “Fight Moments, Captured” (YouTube Thumbnails)

The idea

A visual gallery of fight moments. Something you can browse, filter by bot or season, and click into.

The data problem

I needed actual fight images. Scraping and hosting images directly raises copyright issues and storage costs. I needed a free, always-available source of real fight visuals.

The thumbnail trick

This one didn’t need a separate Bright Data product. Every YouTube video has a publicly available thumbnail at a predictable URL. I reused the video IDs from the YouTube Scraper data and constructed thumbnail URLs automatically.

The gallery shows 35 fight moments with real images, filterable by media type, bot, and season. No images hosted on my servers. Zero storage cost. See the gallery.

The Part Nobody Talks About: Data Cleanup

Here’s the thing nobody mentions in “I built X with Y API” posts: the scraping is the easy part. The data cleanup is where you actually spend your time.

YouTube returns the same fight uploaded by different channels. “Tombstone vs Minotaur” and “TOMBSTONE VS MINOTAUR — FULL FIGHT” are the same fight from different uploaders. Deduplicating on video ID handles that.

But across sources, the same robot appears as “End Game”, “End_Game”, and “EndGame.” I wrote a normalizer, added a manual alias map for the worst offenders, and still spent more time on entity matching than on any single API call.

If you’re building anything that pulls data from multiple web sources, budget twice the time you think you need for normalization. The APIs will work. The data won’t agree with itself.
